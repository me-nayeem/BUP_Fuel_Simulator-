The problem

A simulated Bangladeshi fuel network: 2 depots, 4 stations, 6 routes, 3 fuels, 15-minute ticks. Customers consume fuel every tick; supply ships only reach depots. Someone must decide which depot sends how much of which fuel, on which route, and when — through demand spikes, blocked routes, outages, late or reduced supply, and failing software.

Measured on the real simulator with no action: the first station runs dry at tick 65 (≈16 h) and only 46.1% of demand is served over 2 days.

Our approach

  • Probe first, then design. We measured the simulator before coding: demand model, lifecycle timing, dispatch rules, error formats.
  • One brain, one loop. A single server-side control loop observes, plans and acts every tick; the UI only reads cached state.
  • Explainable optimisation, not a black box. Hour-aware forecast → risk → constraint-safe planner → what-if → action.
  • Human in the loop where it matters. Routine shipments are automatic; risky ones wait for the operator.
  • Resilience as a feature. Every failure mode has a visible, tested behaviour.

Key insight

We verified on 2,304 observations that demand follows an exact pattern:

demand/tick = daily profile ÷ 96 × hour factor × region factor × spike multiplier × (±10% noise)

Industrial demand jumps 3.4× at 06:00. A moving average lags that jump; our model sees it coming. We still calibrate online against real observations and report the forecast error.

What makes it unique

  • Event look-ahead: reads scheduled crises and avoids a route before it is disrupted; pre-scales forecasts for upcoming demand spikes.
  • Shared-budget planner: depot stock and per-tick dispatch capacity are deducted across all shipments in the same tick — no 409 rejections.
  • Auto-cancel doomed shipments: pending shipments on a route about to be disrupted are cancelled and re-routed (fuel returns to the depot).
  • Stable idempotency keys: retries and duplicate app instances can never double-ship.
  • Measured proof: a built-in deterministic experiment runner compares strategies on identical scenarios.
  • Grounded AI: OpenAI explains decisions and incidents from live facts only, never executes, and falls back to built-in text.

What happens every tick — the engineering loop

The brief's loop, implemented as one server-side cycle that runs on every simulator tick (and every 500 ms if the stream is down).
OBSERVESSE event arrives → read 10 REST resources in parallel → one WorldState
DETECTlow stock, active + scheduled crises, disrupted routes, stale data, API faults
PREDICThour-aware demand for the next 24 ticks per station × fuel; time-to-empty
DECIDErank risks; pick depot, route, quantity inside every hard limit
SIMULATEreplay the projection with the shipment: risk 91 → 18, hours left before → after
ACTautopilot sends routine shipments; risky ones wait for approval; doomed ones are cancelled
MONITORshipment lifecycle, service level, forecast error, latency, component health
RECOVERretry, circuit breaker, last-known-good, fallback planner, SSE reconnect

Crisis handling

EventHow the system responds
Demand spikeforecast × multiplier inside the window, pre-stock before it starts, risk re-ranked
Route disruptionroute excluded before departure, pending shipments cancelled, alternate route (e.g. Patiya → Mirpur)
Station outageno shipments to the station; stock kept for others
Depot constraintstill shippable, used last, needs operator review
Shipment delay / shortfallupdated supply schedule flows into depot budgets

Human in the loop

ASSISTED (default) automates routine shipments and sends consequential ones — cross-region, constrained depot, active crisis, uncertain forecast, fallback planner — to the Decisions page with the reason, alternatives, risk before → after and an Explain with AI button. Approvals re-check the latest state first.

Multi-stage Dockerfile, non-root runtime, health checks, env-only config (no secrets in code). GitHub Actions: lint → typecheck → 32 unit tests → build → compose up → health + API smoke test.

Evidence for judges

  • Strategy Comparison page: re-runs all scenarios on demand and stores results in PostgreSQL.
  • System Health page + /api/metrics: live latency, error rate, resources.
  • k6 script (load/dashboard.js): 100 virtual users on the dashboard path + 20 req/s on the decision API, with p95 < 500 ms thresholds.
  • Scenario Control: inject any crisis or fault live and watch the platform respond.

Engineering discoveries we fixed

  • Health checks proxied to the simulator exhausted its 15-connection pool under load → cached, shared probes + 4-request cap.
  • Supply schedule ends at tick 212 → evaluation uses the supplied 2-day window.
  • Replayed allocations return 201 (guide says 200) → both accepted.
